# Feature Specification: LLM Proxy

**Feature Branch**: `1-llm-proxy`
**Created**: 2026-03-02
**Status**: Draft
**Input**: User description: "LLM Proxy — прокси-сервер между клиентами и провайдерами LLM с очередью приоритетов, кэшированием и метриками"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Basic Chat Completion (Priority: P1)

Как клиент системы, я хочу отправлять запросы к LLM через прокси-сервер и получать ответы,
чтобы использовать возможности языковой модели без прямой интеграции с провайдером.

**Why this priority**: Это базовая функциональность прокси - без неё система не имеет смысла.
Все остальные функции строятся поверх базовой возможности проксирования запросов.

**Independent Test**: Можно протестировать отправку POST запроса на `/v1/chat/completions`
с телом `{messages: [{role: "user", content: "Hello"}]}` и получить ответ от GigaChat.

**Acceptance Scenarios**:

1. **Given** прокси-сервер запущен и доступен, **When** клиент отправляет POST `/v1/chat/completions`
   с корректным JSON телом, **Then** возвращается ответ с завершением и HTTP статусом 200
2. **Given** прокси-сервер запущен, **When** запрос не содержит поле `messages`, **Then**
   возвращается HTTP статус 400 с кодом ошибки `invalid_request`
3. **Given** прокси-сервер запущен, **When** запрос содержит `stream: true`, **Then**
   возвращается HTTP статус 400 с сообщением "Streaming is not supported"

---

### User Story 2 - Priority Queue Management (Priority: P1)

Как оператор системы, я хочу управлять приоритетами запросов через очередь,
чтобы критические запросы обрабатывались быстрее обычных при высокой нагрузке.

**Why this priority**: Очередь приоритетов - ключевое отличие системы от простого прокси.
Без неё невозможно управлять нагрузкой и гарантировать SLA для важных запросов.

**Independent Test**: Можно протестировать отправку запросов с разными приоритетами
(через заголовок `X-Priority`) и проверить порядок их обработки.

**Acceptance Scenarios**:

1. **Given** очередь пуста и есть свободные слоты, **When** приходит запрос с приоритетом p1,
   **Then** запрос немедленно отправляется провайдеру
2. **Given** все слоты заняты, **When** приходит запрос, **Then** запрос добавляется в очередь
   соответствующего приоритета
3. **Given** в очереди есть запросы разных приоритетов, **When** освобождается слот,
   **Then** первым обрабатывается запрос с наивысшим приоритетом
4. **Given** очередь заполнена до максимума, **When** приходит новый запрос,
   **Then** возвращается HTTP статус 429 с кодом ошибки `queue_overflow`

---

### User Story 3 - Response Caching (Priority: P2)

Как клиент системы, я хочу получать кэшированные ответы на повторные запросы,
чтобы сократить задержку и уменьшить количество вызовов к провайдеру.

**Why this priority**: Кэширование значительно улучшает производительность и снижает затраты,
но система может работать и без него (с отключённым кэшем).

**Independent Test**: Можно отправить одинаковый запрос дважды и проверить,
что второй ответ пришёл из кэша (по заголовкам или времени ответа).

**Acceptance Scenarios**:

1. **Given** кэш пуст, **When** приходит уникальный запрос, **Then** ответ сохраняется в кэш
   с вычисленным ключом
2. **Given** в кэше есть ответ на запрос, **When** приходит идентичный запрос,
   **Then** возвращается кэшированный ответ без вызова провайдера
3. **Given** запись в кэше устарела (превышен TTL), **When** приходит соответствующий запрос,
   **Then** вызывается провайдер и кэш обновляется
4. **Given** кэш отключён (LLM_CACHE_ENABLED=false), **When** приходит запрос,
   **Then** провайдер вызывается всегда

---

### User Story 4 - Observability & Metrics (Priority: P2)

Как оператор системы, я хочу видеть метрики работы прокси,
чтобы мониторить производительность и выявлять проблемы.

**Why this priority**: Метрики критически важны для эксплуатации, но система может
функционировать без них (хотя и с ограниченной наблюдаемостью).

**Independent Test**: Можно запросить GET `/metrics` и получить метрики в формате Prometheus.

**Acceptance Scenarios**:

1. **Given** прокси обрабатывает запросы, **When** запрашивается GET `/metrics`,
   **Then** возвращаются счётчики запросов с лейблами endpoint, priority, status
2. **Given** запрос был обработан, **When** смотрим метрики, **Then** время ожидания в очереди
   записано в гистограмму `llm_proxy_queue_wait_seconds`
3. **Given** запрос был отклонён из-за переполнения очереди, **When** смотрим метрики,
   **Then** счётчик `llm_proxy_queue_overflow_total` инкрементирован

---

### User Story 5 - Chat Invoke with Metrics (Priority: P3)

Как клиент системы, я хочу получать метрики выполнения в теле ответа,
чтобы анализировать производительность без парсинга заголовков.

**Why this priority**: Удобная функциональность для анализа, но не критична -
метрики доступны и через заголовки.

**Independent Test**: Можно отправить POST `/v1/chat/invoke` и получить ответ
с полем `metrics` в теле.

**Acceptance Scenarios**:

1. **Given** прокси обрабатывает запрос, **When** отправляется POST `/v1/chat/invoke`,
   **Then** ответ содержит объект `metrics` с полями `queue_wait_ms`, `provider_latency_ms`,
   `priority`

---

### User Story 6 - Health Check (Priority: P3)

Как оператор системы, я хочу проверять здоровье сервиса через специальный эндпоинт,
чтобы настроить мониторинг и load balancing.

**Why this priority**: Стандартная функциональность для любого сервиса,
но система работает и без неё.

**Independent Test**: Можно запросить GET `/health` и получить статус "ok".

**Acceptance Scenarios**:

1. **Given** прокси-сервер запущен, **When** запрашивается GET `/health`,
   **Then** возвращается JSON `{status: "ok", env: <environment>}`

---

### Edge Cases

- Что происходит при некорректном JSON в теле запроса? → HTTP 400 с кодом `invalid_request`
- Что происходит при null содержимом сообщения? → Ошибка валидации
- Что происходит при неизвестном приоритете? → HTTP 400 с кодом `invalid_request`
- Что происходит при параллельных идентичных запросах? → Дедупликация через in-flight кэш
- Что происходит при ошибке десериализации записи кэша? → Запись удаляется, счётчик misses инкрементируется
- Что происходит если приоритет по умолчанию отсутствует в конфигурации? → Используется первый приоритет

## Requirements *(mandatory)*

### Chat API Requirements

- **FR-CHAT-001**: Система ДОЛЖНА предоставлять эндпоинт `POST /v1/chat/completions`, совместимый с GigaChat API
- **FR-CHAT-002**: Ответ ДОЛЖЕН включать поле `request_id`
- **FR-CHAT-003**: Заголовки ответа ДОЛЖНЫ включать: `x-llm-proxy-request-id`, `x-llm-proxy-queue-wait-ms`,
  `x-llm-proxy-provider-latency-ms`, `x-llm-proxy-priority`
- **FR-CHAT-004**: При некорректном JSON система ДОЛЖНА возвращать HTTP 400 с кодом ошибки `invalid_request`
- **FR-CHAT-005**: При отсутствии поля `messages` система ДОЛЖНА возвращать HTTP 400
- **FR-CHAT-006**: При `stream: true` система ДОЛЖНА возвращать HTTP 400 с сообщением "Streaming is not supported"

### Chat Invoke Requirements

- **FR-INVOKE-001**: Эндпоинт `POST /v1/chat/invoke` ДОЛЖЕН включать объект `metrics` в тело ответа
  с полями: `queue_wait_ms`, `provider_latency_ms`, `priority`

### Priority Requirements

- **FR-PRIORITY-001**: При отсутствии приоритета ДОЛЖЕН использоваться сконфигурированный приоритет по умолчанию
- **FR-PRIORITY-002**: Заголовок `highest` или `p0` ДОЛЖЕН разрешаться на первый уровень приоритета (p1)
- **FR-PRIORITY-003**: Заголовок `lowest` ДОЛЖЕН разрешаться на последний уровень приоритета
- **FR-PRIORITY-004**: При некорректном приоритете ДОЛЖЕН возвращаться HTTP 400 с кодом ошибки `invalid_request`

### Queue Requirements

- **FR-QUEUE-001**: Уровни приоритета ДОЛЖНЫ конфигурироваться через переменные окружения
- **FR-QUEUE-002**: Каждый приоритет ДОЛЖЕН иметь максимальное количество параллельных слотов
- **FR-QUEUE-003**: Хотя бы один приоритет ДОЛЖЕН иметь вместимость > 0
- **FR-QUEUE-004**: Приоритет по умолчанию: `p2`
- **FR-QUEUE-005**: При превышении `LLM_QUEUE_MAX_LEN` ДОЛЖНА выбрасываться `QueueOverflowError`
- **FR-QUEUE-006**: Запросы с более высоким приоритетом ДОЛЖНЫ отправляться первыми
- **FR-QUEUE-007**: В рамках одного приоритета ДОЛЖЕН поддерживаться порядок FIFO
- **FR-QUEUE-008**: Метод `snapshot()` ДОЛЖЕН возвращать `{queue_len: {...}, in_flight: {...}}`

### Cache Requirements

- **FR-CACHE-001**: Записи кэша ДОЛЖНЫ сохраняться в базе данных
- **FR-CACHE-002**: Ключ кэша ДОЛЖЕН генерироваться как SHA-256 hex digest детерминированной JSON кодировки
- **FR-CACHE-003**: При возрасте записи > TTL get() ДОЛЖЕН возвращать null
- **FR-CACHE-004**: Параллельные запросы для одного ключа ДОЛЖНЫ дедуплицироваться
- **FR-CACHE-005**: Метод `stats()` ДОЛЖЕН возвращать `{hits, misses, sets, expired}`
- **FR-CACHE-006**: При `enabled=False` операции get/set НЕ ДОЛЖНЫ выполняться

### API Data Transfer Requirements

- **FR-DTO-001**: Все входящие запросы от клиентов ДОЛЖНЫ приниматься через типы из библиотеки
  langchain4j-gigachat (ChatCompletionRequest, ChatMessage и др.)
- **FR-DTO-002**: Все исходящие ответы клиентам ДОЛЖНЫ использовать типы из langchain4j-gigachat
- **FR-DTO-003**: Типы langchain4j-gigachat ДОЛЖНЫ использоваться для передачи данных провайдеру GigaChat
  без дополнительного преобразования в другие форматы

### Provider Integration Requirements

- **FR-PROV-001**: Клиент ДОЛЖЕН конфигурироваться с `api_key`, `base_url`, `timeout`, `model` из настроек
- **FR-PROV-002**: При сконфигурированной модели переопределения все запросы ДОЛЖНЫ использовать её
- **FR-PROV-003**: Ключ кэша ДОЛЖЕН включать `base_url` для различения провайдеров

### Request ID Requirements

- **FR-RID-001**: При отсутствии заголовка `x-request-id` система ДОЛЖНА генерировать UUID
- **FR-RID-002**: Заголовок `x-request-id` ДОЛЖЕН добавляться в ответ
- **FR-RID-003**: При наличии заголовка в запросе, то же значение ДОЛЖНО возвращаться в ответе

### Health Check Requirements

- **FR-HEALTH-001**: Эндпоинт `GET /health` ДОЛЖЕН возвращать `{status: "ok", env: <environment>}`

### Metrics Requirements

- **NFR-METRIC-001**: Счётчик `llm_proxy_requests_total` ДОЛЖЕН инкрементироваться с лейблами
  `endpoint`, `priority`, `status`, `error_code`
- **NFR-METRIC-002**: Гистограмма `llm_proxy_queue_wait_seconds` ДОЛЖНА записывать время ожидания
- **NFR-METRIC-003**: Gauge `llm_proxy_queue_length` ДОЛЖЕН отражать текущую длину очереди
- **NFR-METRIC-004**: Gauge `llm_proxy_in_flight` ДОЛЖЕН отражать количество запросов в обработке
- **NFR-METRIC-005**: Эндпоинт `GET /metrics` ДОЛЖЕН возвращать метрики в формате Prometheus

### Key Entities

- **ChatCompletionRequest**: Запрос на завершение чата с полями model, messages, temperature, top_p,
  max_tokens, stop, stream. **Использует тип из langchain4j-gigachat как DTO в контроллерах.**
- **ChatMessage**: Сообщение в чате с ролью (system, user, assistant, tool) и содержимым.
  **Использует тип из langchain4j-gigachat как DTO в контроллерах.**
- **ChatCompletionResponse**: Ответ на запрос завершения чата.
  **Использует тип из langchain4j-gigachat для передачи ответа клиенту.**
- **QueueMetrics**: Метрики очереди с полями queue_wait_ms, provider_latency_ms, priority, endpoint
  (внутренний тип прокси, не из langchain4j-gigachat)
- **PrioritySlot**: Конфигурация слота приоритета с именем (p1, p2, p3) и максимальной вместимостью
  (внутренний тип прокси, не из langchain4j-gigachat)
- **CacheEntry**: Запись кэша с ключом (SHA-256), значением (сериализованный ответ) и временной меткой
  (внутренний тип прокси, не из langchain4j-gigachat)

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Прокси обрабатывает запросы с задержкой не более чем на 50ms больше прямого вызова провайдера
  (при пустой очереди и попадании в кэш - мгновенный ответ)
- **SC-002**: Система поддерживает до 100 одновременных запросов в очереди без потери данных
- **SC-003**: Запросы с приоритетом p1 обрабатываются раньше запросов с приоритетом p2 и p3
  при одинаковой позиции в очереди
- **SC-004**: Коэффициент попадания в кэш (cache hit rate) измеряется и экспонируется в метриках
- **SC-005**: Все ошибки возвращаются в унифицированном формате JSON с кодом, статусом и сообщением
- **SC-006**: Время простоя слотов (slot utilization) экспонируется через метрики для каждого приоритета
- **SC-007**: Health check возвращает статус в течение 100ms при здоровой системе

## Assumptions

- Провайдер LLM (GigaChat) доступен и отвечает в пределах настроенного таймаута
- Клиенты используют синхронные запросы (streaming не поддерживается)
- Кэш используется в рамках одного экземпляра приложения (не распределённый)
- Переменные окружения корректно настроены перед запуском
- Для сериализации используется JSON с отсортированными ключами для детерминированности
- Библиотека langchain4j-gigachat (https://github.com/ai-forever/langchain4j-gigachat) предоставляет
  все необходимые типы для запросов и ответов и используется как единый источник DTO для:
  - Приёма входящих запросов от клиентов в контроллерах
  - Передачи данных провайдеру GigaChat
  - Формирования ответов клиентам

## Out of Scope

- Streaming режим (SSE/WebSocket)
- Распределённый кэш между несколькими инстансами
- Аутентификация и авторизация запросов
- Rate limiting на уровне клиента (только очередь приоритетов)
- Поддержка batched requests (несколько запросов в одном HTTP запросе)
- Webhook уведомления о завершении запросов
