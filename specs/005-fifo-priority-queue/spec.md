# Feature Specification: FIFO Priority Queue

**Feature Branch**: `005-fifo-priority-queue`
**Created**: 2026-03-03
**Status**: Draft
**Input**: User description: "Семафоры ограничивают конкурентность для каждого приоритета - мне не нужны ограничения для каждого приоритета, мне важно чтоб выполнялся принцип FIFO в рамках каждого приоритета"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Strict FIFO Processing Within Priority (Priority: P1)

Как разработчик API-прокси, я хочу чтобы запросы с одинаковым приоритетом обрабатывались строго в порядке их поступления (FIFO), чтобы обеспечить предсказуемое поведение для клиентов.

**Why this priority**: Это основное требование пользователя - гарантия порядка обработки запросов. Без этого невозможно предсказать, какой запрос будет обработан следующим.

**Independent Test**: Можно протестировать, отправив серию запросов с одинаковым приоритетом и проверив, что ответы приходят в том же порядке.

**Acceptance Scenarios**:

1. **Given** очередь пуста, **When** отправлены запросы A, B, C с приоритетом P2, **Then** они обрабатываются в порядке A → B → C
2. **Given** в очереди есть запросы с приоритетом P2, **When** добавляется новый запрос с приоритетом P2, **Then** он обрабатывается после всех ранее добавленных P2 запросов
3. **Given** запросы с разными приоритетами в очереди, **When** извлекается запрос, **Then** сначала извлекаются все P1, затем P2, затем P3 (в порядке поступления внутри каждого приоритета)

---

### User Story 2 - Global Priority Ordering (Priority: P2)

Как оператор системы, я хочу чтобы запросы с более высоким приоритетом всегда обрабатывались раньше запросов с более низким приоритетом, независимо от времени поступления.

**Why this priority**: Глобальное упорядочивание по приоритетам - ключевая бизнес-функция для SLA.

**Independent Test**: Можно протестировать, отправив запросы P3, затем P1, и проверить что P1 обработан раньше P3.

**Acceptance Scenarios**:

1. **Given** в очереди запросы P3 и P1, **When** начинается обработка, **Then** P1 обрабатывается первым
2. **Given** обрабатываются P2 запросы, **When** поступает P1 запрос, **Then** P1 запрос обрабатывается следующим (после текущего активного)
3. **Given** много запросов разных приоритетов, **When** очередь обрабатывается, **Then** порядок: все P1 (FIFO) → все P2 (FIFO) → все P3 (FIFO)

---

### User Story 3 - Simplified Configuration (Priority: P3)

Как администратор системы, я хочу упростить конфигурацию очереди, убрав настройки слотов для каждого приоритета, так как они не нужны для моего случая использования.

**Why this priority**: Упрощение конфигурации улучшает поддерживаемость системы, но не критично для функциональности.

**Independent Test**: Можно проверить, что конфигурация работает без указания priority-slots.

**Acceptance Scenarios**:

1. **Given** конфигурация без priority-slots, **When** система запускается, **Then** очередь работает корректно с FIFO упорядочиванием
2. **Given** старая конфигурация с priority-slots, **When** система обновляется, **Then** настройки priority-slots игнорируются с предупреждением в логах

---

### Edge Cases

- Что происходит при переполнении очереди? → Запрос отвергается с ошибкой 429 (существующее поведение сохраняется)
- Что происходит при shutdown? → Текущие запросы завершаются, новые отвергаются (существующее поведение)
- Как обрабатываются retry? → Retry не влияет на позицию в очереди, retry происходит на уровне обработчика

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА обрабатывать запросы с одинаковым приоритетом строго в порядке поступления (FIFO)
- **FR-002**: Система ДОЛЖНА обрабатывать запросы с более высоким приоритетом (меньшее числовое значение) раньше запросов с более низким приоритетом
- **FR-003**: Система ДОЛЖНА использовать единый механизм упорядочивания для всех приоритетов (single priority queue)
- **FR-004**: Система ДОЛЖНА удалить per-priority семафоры, ограничивающие конкурентность
- **FR-005**: Система ДОЛЖНА сохранить защиту от переполнения очереди (max-length)
- **FR-006**: Система ДОЛЖНА сохранить retry механизм с экспоненциальным backoff
- **FR-007**: Система ДОЛЖНА сохранить метрики (длина очереди, время ожидания, retry)

### Key Entities

- **PrioritizedItem**: Элемент очереди, содержащий запрос, приоритет и порядковый номер для FIFO упорядочивания
- **PriorityChannel**: Единая приоритетная очередь с глобальным упорядочиванием
- **QueuedRequest**: Запрос клиента с прикрепленным результатом для асинхронного ожидания

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Запросы с одинаковым приоритетом обрабатываются в порядке поступления (порядок ответов совпадает с порядком запросов)
- **SC-002**: Запросы P1 обрабатываются раньше любых P2 и P3 запросов в очереди
- **SC-003**: Время добавления запроса в очередь не превышает 1 мс (без блокировки на семафорах)
- **SC-004**: Конфигурация priority-slots более не требуется для работы системы
- **SC-005**: Все существующие тесты проходят после изменений

## Assumptions

- Глобальный лимит параллельных запросов к LLM провайдеру контролируется на уровне HTTP клиента или провайдера
- Порядок обработки запросов важнее ограничения конкурентности для каждого приоритета
- Retry механизм работает на уровне обработчика и не влияет на позицию в очереди
- Метрики in-flight будут показывать общее количество запросов в обработке без разбивки по приоритетам (опционально)
