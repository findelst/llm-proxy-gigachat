# Feature Specification: Queue Timeout & Cleanup

**Feature Branch**: `006-queue-timeout`
**Created**: 2026-03-03
**Status**: Draft
**Input**: User description: "Добавить механизм очистки очереди по таймауту. Если сообщение живет в очереди больше заданного времени (например 10 минут), оно должно быть удалено и клиенту должен быть возвращен ответ что очередь переполнена."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Expired Request Cleanup (Priority: P1)

Как клиент API, я хочу получить понятный ответ если мой запрос слишком долго ждёт в очереди, вместо того чтобы ждать бесконечно.

**Why this priority**: Это основное требование - клиенты должны знать что их запрос не будет обработан если система перегружена. Без timeout клиенты могут ждать вечно.

**Independent Test**: Можно протестировать, добавив запрос в очередь с очень коротким timeout и проверив что возвращается ошибка timeout.

**Acceptance Scenarios**:

1. **Given** запрос в очереди дольше настроенного timeout (например 10 минут), **When** срабатывает проверка, **Then** запрос удаляется из очереди и клиент получает ошибку "queue timeout"
2. **Given** очередь пуста, **When** приходит запрос, **Then** он обрабатывается немедленно без timeout
3. **Given** запрос в очереди меньше timeout, **When** срабатывает проверка, **Then** запрос остаётся в очереди

---

### User Story 2 - Configurable Timeout (Priority: P2)

Как оператор системы, я хочу настроить максимальное время ожидания в очереди в зависимости от моих SLA требований.

**Why this priority**: Разные use cases требуют разных timeout. Гибкая конфигурация позволяет адаптировать систему под разные сценарии.

**Independent Test**: Можно протестировать с разными значениями timeout и проверить что cleanup работает корректно.

**Acceptance Scenarios**:

1. **Given** timeout настроен на 5 минут, **When** запрос ждёт 6 минут, **Then** он удаляется с ошибкой timeout
2. **Given** timeout настроен на 30 минут, **When** запрос ждёт 10 минут, **Then** он остаётся в очереди
3. **Given** timeout отключен (0 или -1), **When** запрос в очереди, **Then** он ждёт бесконечно

---

### User Story 3 - Timeout Metrics (Priority: P3)

Как оператор системы, я хочу видеть метрики по timeout запросам чтобы понимать нагрузку на систему.

**Why this priority**: Метрики помогают мониторить систему, но не критичны для базовой функциональности.

**Independent Test**: Можно проверить что метрики записываются при timeout.

**Acceptance Scenarios**:

1. **Given** запрос удалён по timeout, **When** происходит cleanup, **Then** увеличивается счётчик timeout метрик
2. **Given** несколько запросов разных приоритетов удалены, **When** проверяем метрики, **Then** видим разбивку по приоритетам

---

### Edge Cases

- Что происходит если запрос обрабатывается в момент timeout? → Не удалять, дать завершиться
- Что происходит при shutdown приложения? → Завершить обработку активных запросов, вернуть timeout для ждущих
- Что происходит если timeout = 0? → Запрос должен быть отклонён если не может быть обработан немедленно
- Как считается время? → От момента добавления в очередь (queuedAt) до текущего времени

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА удалять запросы из очереди если они ждут дольше настроенного timeout
- **FR-002**: Система ДОЛЖНА возвращать клиенту понятную ошибку когда запрос удалён по timeout (не "queue overflow")
- **FR-003**: Система ДОЛЖНА позволять настраивать timeout в конфигурации (по умолчанию 10 минут)
- **FR-004**: Система ДОЛЖНА записывать метрики timeout событий с разбивкой по приоритетам
- **FR-005**: Система НЕ ДОЛЖНА удалять запросы которые уже начали обрабатываться
- **FR-006**: Система ДОЛЖНА проверять timeout периодически (например каждую минуту)

### Key Entities

- **QueuedRequest**: Запрос в очереди с полем `queuedAt` для отслеживания времени ожидания
- **QueueTimeoutConfig**: Конфигурация timeout с полем `maxWaitTime` (в минутах)

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Запросы ждущие дольше timeout получают ошибку в течение 1 минуты после истечения timeout
- **SC-002**: Клиенты получают понятное сообщение об ошибке (например "Request timed out after waiting 10 minutes in queue")
- **SC-003**: Metрики timeout доступны для мониторинга (счётчик по приоритетам)
- **SC-004**: Активные запросы (в обработке) не затрагиваются cleanup процессом
- **SC-005**: Все существующие тесты проходят после изменений

## Assumptions

- Timeout проверяется периодически, не в реальном времени (компромисс между точностью и производительностью)
- По умолчанию timeout = 10 минут
- Timeout можно отключить установив значение 0 или отрицательное число
- Ошибка timeout отличается от ошибки overflow (разные HTTP коды или сообщения)
- Проверка timeout выполняется в отдельной корутине/потоке
